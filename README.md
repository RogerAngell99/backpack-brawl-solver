# Backpack Brawl Solver

Go CLI solver for Backpack Brawl layouts on a 6x9 backpack grid.

The v1 solver optimizes item placement, rotation, valid star targets, and craft-ready recipes. It does not simulate combat, shop effects, or post-fight replacement of crafted items.

## Quick Start

Validate the catalog:

```powershell
go run ./cmd/backpack-brawl-solver validate-catalog
```

Review the consolidated catalog with shapes, star filters, recipes, and clickable source URLs:

```powershell
go run ./cmd/backpack-brawl-solver review-catalog
```

Item images are stored locally under `assets/items/`, and each catalog item has `image_url` and `image_path`.

Solve a full 6x9 grid with a small inventory:

```powershell
go run ./cmd/backpack-brawl-solver solve --items scalemail,thornwall,armor_kit --top 3
```

Run a saved scenario:

```powershell
go run ./cmd/backpack-brawl-solver solve --scenario scenarios/spinegrowth-basic.json
```

Use counts for duplicate items and control parallelism:

```powershell
go run ./cmd/backpack-brawl-solver solve --items kiwi_dewdrop:2,cactus:4,spinegrowth_breastplate --workers 8 --top 5
```

Use a custom grid:

```powershell
go run ./cmd/backpack-brawl-solver solve --grid "111111111/111111111/111111111/111111111/111111111/111111111" --items golden_skull,poison_potion
```

Extract a review proposal from a saved wiki item page:

```powershell
go run ./cmd/backpack-brawl-solver import-html "C:\Users\roger\Downloads\Cactrio - Backpack Brawl Wiki.html"
```

Extract every saved wiki item page from a folder:

```powershell
go run ./cmd/backpack-brawl-solver import-html "C:\Users\roger\Downloads"
```

The default `import-html` output is a human review report. Use `--json` when you need the raw data proposal:

```powershell
go run ./cmd/backpack-brawl-solver import-html --json "C:\Users\roger\Downloads"
```

Grid format is 6 rows by 9 columns:

- `1` = usable backpack space
- `0` = unavailable space

The CLI uses a deterministic search limit by default so larger inventories return promptly. Use `--max-nodes 0` for an exhaustive run.

## Scenario Files

Scenarios let you save a real backpack and item list as JSON:

```json
{
  "name": "spinegrowth-basic",
  "grid": [
    "111111111",
    "111111111",
    "111111111",
    "111111111",
    "111111111",
    "111111111"
  ],
  "items": {
    "scalemail": 1,
    "thornwall": 1,
    "armor_kit": 1
  },
  "top": 3,
  "workers": 1,
  "max_nodes": 0,
  "no_skips": false,
  "stop_on_coverage_ceiling": false,
  "priority_semantics": "outgoing-v2",
  "priorities": [
    "craft:spinegrowth_breastplate",
    "star_source:scalemail"
  ]
}
```

Command-line flags override scenario values:

```powershell
go run ./cmd/backpack-brawl-solver solve --scenario scenarios/spinegrowth-basic.json --top 10 --workers 8
```

`priorities` is optional. Use `craft:<item_id>` for a craft result and `star_source:<item_id>` for stars generated by one item source. `priority_semantics` controls loose `star_source:*` priorities:

| Semantics | Measures | Three copies hitting the same four targets |
| --- | --- | --- |
| `outgoing-v2` | Distinct target instances reached by all copies combined | 4 |
| `outgoing-per-instance-v3` | Sum of distinct target instances reached by each copy | 12 |
| `legacy-incoming-v1` | Legacy incoming coverage behavior | depends on source coverage |

Use `outgoing-v2` when spreading stars across different targets is the goal. Use `outgoing-per-instance-v3` when every copy independently benefits from its own star targets, such as several Spices each reaching the same Food cluster. The latter counts static source-to-target links, not temporal combat activations.

To prioritize incoming convergence, configure `coverage_groups` explicitly and include the corresponding `coverage_group:<index>` key in `priorities`; loose `star_source:*` entries are not converted into groups. The web client lets you select either outgoing semantics and defaults to `outgoing-v2`. To preserve an incoming intent when moving a saved scenario to an outgoing mode, add an explicit coverage group and its priority key.

For explicit coverage groups, if `stop_on_coverage_ceiling` is true and `top` is 1, the solver may stop after reaching the theoretical best coverage bucket; this is faster, but later tie-breakers may not be fully optimized. `outgoing-per-instance-v3` also supports `stop_on_priority_ceiling`: it stops only after every requested source priority reaches a safe structural maximum. This proves the priority vector but not star-count tie breakers. Coverage-group solves use a deterministic coverage seed. Outgoing solves without an explicit group use a runtime-valid directed-star seed in limited mode, including no-skips layouts. Output metadata distinguishes coverage and star seeds.

The same option is available in the CLI:

```powershell
go run ./cmd/backpack-brawl-solver solve --scenario scenarios/spinegrowth-basic.json --stop-on-coverage-ceiling
```

## Development

Run the test suite:

```powershell
go test ./...
```

Run the browser E2E tests:

```powershell
cd web
npm install
npx playwright install chromium
npm run test:e2e
```

The E2E suite starts Vite and mocks remote solver responses so visual interaction
tests remain deterministic and do not require the WASM solver.

Run benchmarks:

```powershell
go test ./internal/solver -bench .
```

Run the reproducible solver-quality suite:

```powershell
go run ./cmd/backpack-brawl-solver benchmark-scenarios --dir benchmarks/scenarios --budgets 250000,1000000,5000000,20000000,100000000 --repeat 3 --workers 1 --out benchmark-current.json
```

Run the frozen diagnostic profile for the principal V3 scenario and the player-debug regression. It records one-worker incumbent events at the evaluation that changed the score, separate charged and uncharged work, packing layers, priority-ceiling distribution, plateau classification, and the literal plus physical layout identities:

```powershell
go run ./cmd/backpack-brawl-solver benchmark-scenarios --dir benchmarks/scenarios --scenarios outgoing-per-instance-food,outgoing-debug-reference-v3 --budgets 1000000,5000000 --repeat 3 --workers 1 --diagnostic --out diagnostic-current.json
```

`--diagnostic` requires exactly one worker. Repetitions remain separate timing samples in JSON; they are not interpreted as distinct quality outcomes. The first priority ceiling is classified as `early` before 25% of the charged budget and `late` after 75%. A strong plateau requires the first ceiling and last score improvement by 40%, plus at least eight canonical physical layouts at that ceiling.

Use `--repair-search-mode off` or `--repair-search-mode on` to compare repair search against the same scenario set without duplicating JSON files.

Compare two benchmark reports:

```powershell
go run ./cmd/backpack-brawl-solver compare-benchmarks benchmark-baseline.json benchmark-current.json
```

The benchmark suite measures best-found quality at fixed node budgets first, then reports elapsed time and nodes/sec as secondary metrics.

`benchmarks/scenarios/outgoing-per-instance-food.json` is the principal Spirit Biscuit plus three Spice V3 profile. `benchmarks/scenarios/outgoing-debug-reference-v3.json` is the 24-item, 12-priority player-debug regression oracle. Reports record the catalog SHA-256, build revision, workers, flags, priorities, and seed/bound/symmetry metrics. Recommended comparison budgets are `250000,1000000,5000000,20000000,100000000` with one worker.

## Manual Layout Comparison

Use **Manual layout comparison** in the web UI to paste a JSON array of placements, evaluate it locally, and copy the detailed report containing placements and every realized star link. Each entry needs `item_id`, `rotation`, and `origin`; `instance_id` is optional and is assigned by inventory order when omitted.

```json
[
  { "item_id": "spice", "rotation": 0, "origin": [5, 1] }
]
```

The confirmed player layout is kept as a literal evaluation oracle. It is not passed as an incumbent to automatic search or benchmarks.

## Catalog Status

The catalog is generated from the curated catalog plus the Backpack Brawl 6.1.1
runtime capture. Runtime `types`, shapes, and star positions are authoritative for
every item. It currently contains 1,196 items and 477 valid recipes. New runtime
items are marked with `needs_review: true`, and the 528 captured runtime star graphs
are used before curated star rules. The catalog also contains 27 captured heroes and
confirmed shared/hero-specific item scopes. Unsupported or context-dependent conditions
return `unknown`; the solver does not score those stars as arbitrary targets.

Regenerate it with the procedure documented in `analysis/README.md`. Runtime stats,
levels, rarity, and confidence metadata are available in `data/item-metadata.json`.
Use `hero_filter` in scenario JSON or `--hero`, `--exclude-hero`, and
`--hero-mode shared` in the CLI to restrict item availability by hero.
